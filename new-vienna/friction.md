Friction log of the Projektschau dogfood spike (build-spec Revision 2, step 1): a site-local `process` plugin writes `projekte.json`, the theme's `script.js` mounts Projektschau's renderer on the home page. Each entry says what the plugin guessed or reimplemented that moss already knows, and what the step 3 build contribution has to give it. Tags follow the owner's scoring: FLOOR is something simple that needed more than markdown and conventions, CEILING is something the design needed that moss could only ship through a workaround.

## Result

31 cards render on the home page from `projekte.json`, all 46 project and partner addresses it links answer 200, the five area colour sets match Projektschau's `farben.py` output exactly, and `pruefe.py` reports only the expected embedded-data line. The `_generated` first key is tolerated by both the renderer and `pruefe.py`, so it stays. The plugin is about 330 lines of plain JavaScript; most of it is the parts below that moss already has.

## Gaps, in order of how much the step 3 contribution must close

1. CEILING, page addresses. The process hook runs before render with no page map, so the plugin reimplements moss's slug rule: `generate_slug` from `moss-core/src/slug.rs` (NFC, lowercase, `&` to `and`, apostrophes and punctuation to hyphens, dots kept, 100-character cap), plus "file stem for the page, folder name for each directory". `test.js` checks it against 39 addresses from `moss-cli list --json`. It does not cover duplicate-slug resolution, a `url:` override in frontmatter, a language prefix, or `[terms]` pages. The partner pages (`/partners/otto-glöckel/`) have no source file at all: the plugin assumes the term namespace is `partners` because the site's `config.toml` says `terms.partners`, and assumes the term slug uses the same rule. The contribution must hand the plugin each page's final `url_path` and each term's page address, never ask it to compute them.

2. CEILING, the one line the author writes is invalid. `children_style: projektschau` draws `field 'children_style' has invalid value ... allowed: ["list", "summary", "grid"]` on every build, and `--strict` fails on it. Until a build contribution can register a children style, the home page cannot be declared in frontmatter without a warning. The contribution needs a registered style name (or a plugin-declared one) that validation accepts.

3. CEILING, no way to put a fill into the page. The plugin cannot touch the page, so the theme script finds `.moss-cards-container`, hides it and inserts the mount after the first paragraph, by DOM position. It works because moss still renders its own listing for an unknown style; if moss ever stops listing the children, or the container class changes, the board silently moves to the end of the article. The contribution has to return a fill for the page that lists the children, and replace moss's listing instead of sitting beside it. Hiding is also what keeps the plain list as the no-script fallback, which a fill should keep.

4. CEILING, the data file lands in the author's folder. `projekte.json` is written at the site root through `write_project_file`, so it appears in the client's Finder and Drive and in the git history. The plugin skips the write when the bytes are unchanged (read first, compare), because the folder is synced and a preview watches it; every plugin that writes a source file has to remember this. Writing into the build output, the way `places_data` does, removes the file from the folder and the guard with it. The file carries `"_generated": "by the projektschau plugin; do not edit"` as its only label, which is a convention, not something moss shows.

5. FLOOR, resolved frontmatter and the page graph. The plugin lists files with `list_project_tree`, reads each one and parses frontmatter with its own subset parser (`key: value`, `[a, b]`, quotes, `false`). It does not know what moss knows: `title` falling back to the file name, `uid`, `weight` ordering, `draft` or `listed: false` pages, `lang` and translations, which folder index is a page's home (it takes `is_home` from `list_project_tree`, which is the one piece that was available). A page with `draft: true` would still land on the board. The contribution should pass resolved pages: frontmatter as moss parsed it, `draft` and `listed` already applied, `title` resolved.

6. FLOOR, body to HTML. `beschreibung` and `abschnitte` need the first paragraph and the `## ` lists as HTML. The plugin converts links, `*em*`, `**strong**` and escapes the rest by hand. Anything richer in a first paragraph (relative links, `[[wikilinks]]`, footnotes, inline code, smart quotes) would come out as raw text or a link to a path that is not a page. moss renders the body already; the contribution should pass the rendered body, or the first paragraph and each section as rendered HTML, with links already resolved.

7. FLOOR, status wording and dates live in code. The `years` field gives only years, so the plugin produces `Built 1927–1933`, `Founded 1925 · closed 1934`, `Introduced 1919` and `Held 1931`, and `sortierung` is always `YYYY01`. The hand-written prototype carries "Opened 17 December 1922", "Decided 9 March 1923 · open from 18 June 1925", month-accurate sorting and a different order inside each year (31 of 31 titles, links and descriptions match the prototype's package; status wording differs on 10 projects, `sortierung` on 14, and `nr` order follows from that). The plugin honours an optional `status:` field, which no file uses. Either the files gain a structured date and a status line, or the board accepts the plainer wording; this is an authoring decision, not a moss gap, but it surfaces here because nothing else reads `years`.

8. FLOOR, vocabularies owned by the plugin. The `kind` values (Building, Service, Programme, Event), their order, their verbs and the `icon` names (five Lucide icons embedded as path data) are in the plugin. That is right under ADR-032 (a plugin owns its data format), but a site author has no list of valid values: `kind: Buidling` produces a `buidling` category without a word, a bad `icon` drops the icon silently, a project with an unparseable `years` is skipped silently. The plugin can return `{ success: false }` but the build still reports `process done`; the hook's `message` is not shown on success. Needed: a way for a plugin to report authoring warnings against a file, shown the way the `children_style` warning is.

9. FLOOR, language and site facts. `sprachen: ["en"]` and every interface text are fixed in the plugin. The process context carries `project_info` and `config` but no site language, no list of languages, no site title. The German mirror (step 5) needs the plugin to know which pages are translations of which; today it knows nothing about `lang` or translation pairs.

10. FLOOR, order of areas. Areas come out alphabetical (Education, Health, Housing, Sport, Welfare) unless the folder index carries `weight`; the prototype's order (Housing, Health, Welfare, Education, Sport) needs `weight` on five files this spike was not allowed to edit. Folder order is something moss already resolves for its own listings.

11. FLOOR, theme assets have no stable URL from a script. moss hashes `script.js` (`script.<hash>.js`) but serves `projektschau/projektschau.js` and `.css` under their plain names, so a browser may keep an old copy after a Projektschau upgrade. The script has `mossTheme.base` and nothing that gives it a hashed address. The KERN kit is not in this theme (another agent's), so the screenshots used a scratch copy of the kit linked into the build output.

12. FLOOR, plugin engine. A `process` plugin has `window.__TAURI__.core.invoke` and the host command names (`list_project_tree`, `read_project_file`, `write_project_file`); that is documented only by the fixture plugin in `moss-build/tests` and by `moss-api`'s TypeScript, which a bundle without npm has to read to learn the call shapes. `console.log` takes one argument. `moss-cli describe --json` lists hook names but not the host commands a hook may call. The plugin needed no engine shim: `\p{L}` regexes, `normalize('NFC')`, `Array.from` and `async` all worked in QuickJS. The shims that matter come with step 4 (Projektschau's own renderer needs `DOMParser` and `URL`).

13. FLOOR, `draft: true` does not keep a page out of a build. This file is a note about the site, not a page of it; with `draft: true` it is still built at `/friction/` and listed in `moss-cli list` (flagged `draft,nav-item`), so `listed: false` and `nav: false` were added to hide it from the nav and listings, and it should be deleted before the folder is delivered.

14. FLOOR, tests for plugins. There is no harness to run a hook against a fixture folder; the plugin's logic is a pure function `buildPackage(docs, homes)` run under node with a scratch script that walks the folder, and the only end-to-end check is a real build.

## What a build contribution would need to hand over, in one list

For each page of the folder: source path, `url_path`, resolved frontmatter (including `weight`, `draft`, `listed`, `lang`), rendered body HTML with links resolved, first paragraph, its children and their order, translations. For the site: languages, default language. For the term pages (partners): their addresses. As outputs: files for the build output, and a fill for the page that lists the children, plus a registered `children_style` name so validation accepts the author's one line. Plus a channel for authoring warnings.
